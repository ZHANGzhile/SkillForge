# 退款结局优先级修复：预声明

日期：2026-09-30（Europe/Paris）。本文件、实现、输入和顺序在本轮模型调用前冻结。

## 问题与假设

已观察的 HIGH + FAILED 退款连续三次被模型拒绝，EOC 要求转人工。
工具策略 `eligibility` 先检查 HIGH，再检查支付和金额；模型提示分别描述了这两条规则，未明确冲突时的先后顺序。
这支持“值得测试优先级表达”的假设，不足以证明模型内部的失败原因。

## 固定条件及唯一干预

同一签收 SFT、模型配置、预算、B 执行契约、Gate、幂等与工具二次策略检查。
control 和 priority 都保留上轮已审核的有限域 allowlist 显示转换。
priority 仅在 refund 的 policy 末尾追加固定文本，明确 HIGH 优先于支付/金额拒绝、缺失风险需读取、Gate 不适用不等于拒绝。
文本不读取隐藏环境、EOC、任务 ID 或结果，不推导状态、不调用工具、不替换模型 Action。
这是人工策略表达修复，不能归因于失败边界学习。

## 顺序、样本与准入

1. 完整边界 validation 23 个场景，两组各一次完整任务和一次固定候选决策，共 92 条执行记录。每次决策的授权读取单独计费。
2. 验证结束后才计算准入：priority 的 EOC 总数、正常完成数、固定候选正确数均不得低于新跑 control；实际违规必须为零，模型违规尝试不得增加。逐场景改善和退步全部报告。
3. 仅通过上述研究准入后，对已见的全部 8 个 refund test 场景做诊断重放：两组、两种评测、各三次，共 96 条；不按成功与否选择任务。拒绝则停止，不修改同版候选救分。
4. 每阶段按 seed 与 job key 哈希混合顺序串行请求服务。两组模型请求均新执行，不复用历史分数或别名。完整任务从相同数据库和故障队列开始。

完整任务按原 EOC 和状态链验收。固定候选经过相同授权 get_order/get_payment/get_customer（地址族额外验证地址），提供同一 B；正确动作按 EOC 指定 Skill/refuse/escalate，Skill 名与参数必须一致。固定候选仅用于受限决策，不代表自由规划能力。

## 审核与报告

保存原 context、实际发送 JSON 字符串、模型身份、动作、完整工具审计、checkpoint 哈希、阶段选择和最终文件清单。
恢复前审核全部已存记录；基础设施失败停止，不计成业务失败；模型输出格式错误保留为失败。
统计 EOC、正常完成、refuse/escalate 分布、固定候选正确数、违规尝试与实际违规、被拒写入、Skill 次数、模型/token/工具/Gate 成本。
按独立场景对完整任务和决策的差值 bootstrap 95% 区间；重复次数不增加独立场景数，8 场景区间仅描述本样本。
新方案冻结旧核心与原始研究文件，不改变线上部署。完整主项目 69 项 validation 与 78 项 test 尚未成为本候选的产品准入证据；不能凭此次局部诊断宣布产品全部修复。
